# pal-chat 项目章程（MVP）

状态：初始化基线  
关联议题：OT-17  
更新时间：2026-07-24

## 1. 产品目标

pal-chat 是一个前后端分离的多 Agent 群聊 Web 项目。它通过上下文结构、Agent
响应决策与群聊编排，使多个 Agent 的参与更接近真实群聊：该回应的成员回应，
不相关的成员保持沉默，回复能理解群聊中“谁对谁说了什么”，同时让用户可理解、
可控制 Agent 的行为。

MVP 首先验证一个核心假设：

> 相比“每条消息让所有 Agent 依次回答”，基于相关性、角色和对话状态进行响应
> 决策，能在可控成本下显著提升多 Agent 群聊的自然度和有效信息密度。

## 2. 目标用户与核心场景

### 目标用户

- 希望在同一会话中使用多个角色化 AI 助手的个人用户。
- 需要观察、研究或二次开发多 Agent 对话编排的开发者。

MVP 默认采用“单用户、单工作区、文本聊天”的产品假设；是否支持公开注册和
多租户须在进入生产化阶段前另行决策。

### 核心用户故事

1. 作为用户，我可以创建一个群聊并加入 2–5 个具有不同名称、角色和提示词的
   Agent，以便建立清晰的参与者结构。
2. 作为用户，我发送一条消息后，只看到与话题相关或被点名的 Agent 参与，
   无需阅读所有 Agent 的机械轮流回复。
3. 作为用户，我可以从消息界面看出发送者、回复关系、进行中状态和失败状态，
   并能停止本轮生成或重试失败回复。
4. 作为用户，我可以重新打开历史会话，并保持消息顺序、参与者与必要上下文。
5. 作为项目团队，我可以用固定场景重复评估响应决策、上下文正确性、时延与
   模型成本，判断优化是否真实有效。

## 3. MVP 范围与优先级

### P0：必须具备

- 群聊与成员：创建/进入群聊，配置 2–5 个 Agent 的名称、角色和系统提示。
- 文本消息：发送用户消息，展示 Agent 回复、发送者、时间、生成/失败状态。
- 响应决策：支持显式点名优先、相关 Agent 参与、不相关 Agent 沉默；设置单轮
  最大回复数，避免无限互相触发。
- 上下文：保留共享对话事实，同时向各 Agent 提供角色相关上下文；回复关系与
  消息顺序必须明确，不能把其他 Agent 的话误认为用户指令。
- 编排控制：支持流式展示、停止本轮、失败重试、超时和可读错误信息。
- 持久化：保存群聊、成员配置和消息历史，并能重新打开。
- 可观测性：开发环境记录每轮候选 Agent、选择结果、未响应原因、模型调用耗时
  和 Token/成本信息；日志不得记录密钥。
- 评估基线：建立覆盖点名、开放讨论、角色不相关、追问、打断、失败重试的固定
  场景集，并保留结果。

### P1：验证后增强

- 用户手动邀请某 Agent 补充、对单条 Agent 回复重新生成。
- 对话摘要或分层记忆，以控制长会话上下文与成本。
- Agent 并行/串行回复策略和更细的房间级参数。
- 自适应移动端 Web 布局与基础无障碍增强。

### 非目标

- 原生移动端、语音/视频、图片生成或复杂附件处理。
- Agent 自主调用外部工具、执行代码或修改外部系统。
- 公开 Agent 市场、社交关系、多人实时协作。
- 企业多租户、计费、配额、SLA、生产级管理后台。
- 模型训练或微调。
- 本初始化阶段的生产部署、真实用户数据迁移和商业发布时间承诺。

## 4. 关键产品规则

### 响应决策

- 被明确点名的 Agent 默认进入候选集；未点名 Agent 依据角色相关性和对话状态
  判断是否参与。
- 每轮设最大参与 Agent 数、最大 Agent 间接力轮数和整体超时。
- “保持沉默”是一等结果，需要可记录原因，但不在普通聊天界面制造噪声。
- Agent 的自动回复不能无限触发其他 Agent；新一轮接力必须由编排器显式批准。
- 用户随时可以停止生成，停止后已落库内容与未完成状态必须一致可解释。

### 上下文边界

- 消息必须包含稳定 ID、发送者类型/ID、时间、所属会话和可选回复目标。
- 共享上下文用于群聊公共事实；角色私有提示、凭据和内部决策不得混入公开消息。
- 编排决策输入与最终发给模型的上下文应可追踪，但不得向终端用户泄露系统提示、
  密钥或内部推理。
- 长会话裁剪/摘要不得改变说话人、回复关系和关键事实。

## 5. MVP 验收标准

### 功能验收

1. 用户可创建含 2–5 个 Agent 的群聊，发送消息并看到至少一个有效回复。
2. 在固定点名场景中，被点名 Agent 会参与；无关 Agent 不产生可见回复。
3. 单轮回复达到配置上限、超时或用户停止后，不再产生新的 Agent 回复。
4. 刷新或重新进入后，群聊成员、消息内容、顺序、发送者和状态保持一致。
5. 任一模型调用失败时，界面显示可重试的错误，不导致整段会话丢失或重复落库。
6. 开发日志可以关联一次用户消息、候选 Agent、实际参与者、耗时和用量，且不含
   API Key、完整系统提示等敏感信息。

### 质量验收

- 对约定的评估场景集至少连续运行 3 次，记录每次参与者选择、上下文错误、
  首个回复时延和模型用量；在形成基线前不预设虚假的百分比目标。
- 自动化测试至少覆盖响应上限、点名路由、重复消息幂等、超时/重试、持久化顺序
  和敏感信息不落日志。
- 支持的主流桌面浏览器范围、性能预算与安全基线由架构和 QA 在 M0 决策后写入，
  未确认前不得宣称“生产可用”。

## 7. 里程碑与进入/退出条件

### M0：规格与技术基线

- 输入：本章程。
- 输出：架构基线、UX 核心流程、测试/评估策略、待决策项结论。
- 退出条件：接口与消息模型、模型供应商策略、存储、隐私边界、开发运行方式和
  P0 验收可测试；未解决的高风险项有负责人。

### M1：端到端纵向切片

- 输出：一个用户、一个群聊、2–3 个 Agent 的创建—发言—决策—流式回复—落库
  闭环。
- 退出条件：P0 主路径可本地重复运行，基础测试通过，失败不会破坏会话数据。

### M2：自然度与上下文优化

- 输出：点名、相关性、沉默、接力上限、长上下文策略及固定评估结果。
- 退出条件：相对 M1 基线有可复核改善；成本、时延和误参与的取舍有决策记录。

### M3：MVP 硬化与验收

- 输出：异常/权限/兼容/回归测试、运行文档、安全检查和已知限制。
- 退出条件：P0 验收全部有证据；Ripley 给出质量结论；产品负责人确认范围完成。
- 不包含生产发布；发布需要独立授权与发布清单。

## 8. 启动依赖与待决策项

以下决策会显著改变实现范围，须在 M0 关闭：

1. 首个模型供应商、是否允许多供应商，以及开发/测试调用预算。
2. MVP 身份模型：纯本地单用户、受限测试账号，还是公开注册。
3. 数据库与部署目标；开发、测试、生产环境是否隔离。
4. 对话数据保留/删除规则，系统提示与模型凭据的存储方式。
5. 首版支持的 Agent 数、单轮最大回复数、超时和成本上限。
6. “自然群聊”的基线样本、评价人和最小可接受改进标准。
7. 许可证已采用 MIT；仍需确认第三方模型 SDK、UI 素材和字体许可证兼容性。

## 9. 主要风险与应对

| 风险 | 影响 | 首要应对 |
| --- | --- | --- |
| 所有 Agent 抢答或互相无限触发 | 噪声、成本失控 | 硬性轮次/参与数上限，决策与生成分离 |
| 上下文串线、角色混淆 | 回答错误、提示注入风险 | 结构化消息、角色边界、固定回归场景 |
| 长会话导致时延和成本增长 | 体验不可持续 | 用量可观测，后续引入裁剪/摘要并做事实回归 |
| 流式、重试导致重复落库或乱序 | 历史不可相信 | 消息 ID、幂等键、状态机和并发测试 |
| 过早建设多租户/工具生态 | MVP 失焦 | 严守非目标，新增范围必须更新章程并重新评估 |
| 缺少真实评价基线 | 无法证明“更自然” | M0 建立场景集与人工评分规则，再做优化 |
| 密钥或敏感对话泄露 | 安全与信任受损 | Secret 管理、日志脱敏、数据保留规则和安全测试 |

## 10. 变更与验收规则

- 新增 P0 能力、改变目标用户、引入外部工具执行、多用户/多租户或生产发布，
  均视为范围变更，必须记录价值、成本、风险和验收变化后再决定。
- 代码完成不等于需求完成；每项 P0 必须同时有行为证据、测试结果和已知限制。
- 关键决策采用 ADR 或本章程的决策记录，不以聊天中的临时结论替代。
- 本章程中的单用户、文本聊天和 2–5 Agent 是 MVP 假设；用户确认或证据变化后
  可以更新，但不得静默扩大。
