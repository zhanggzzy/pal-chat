# pal-chat 产品简报（首版 Demo）

状态：产品方向已确认，待架构拆解
关联议题：OT-17  
更新时间：2026-07-28

## 1. 目标

pal-chat 是一个个人技术验证 Demo。它要验证：

> 一个真人用户与两个轻量 LLM Agent 组成的三人群聊，在 Agent 能够主动发言、
> 回应彼此、追问、沉默、打岔并恢复旧话题的情况下，可以多接近真实群聊，而
> 不是两个 Agent 机械轮流回答。

首版不是通用 Agent 平台，也不追求生产可用。产品价值在于让群聊行为背后的
话题选择、上下文组装和响应决策可观察、可解释、可复盘。

## 2. 产品形态

一个前后端分离的单页 Web 实验台，桌面端页面约分为两部分：

### 聊天区

- 固定显示一名用户和两个具有不同角色的轻量 Agent。
- 使用常见即时通讯布局，展示发送者、消息顺序和生成状态。
- 用户可以发起话题、切换话题、回到旧话题，并随时插话或停止自动接力。
- Agent 可以回应用户或另一个 Agent，也可以主动补充、提问、连续发言或沉默。

### 分析区

按消息、话题链和 Agent 查看：

- 当前话题链列表及 active/inactive 状态；
- 新消息被创建、关联或重新激活到哪个话题链；
- 每个 Agent “自己眼中”的话题链索引；
- 本次实际选入 Agent 上下文的消息或摘要；
- 上下文 Token 数；
- Agent 的 `回应 / 沉默` 结构化决策；
- 参与评分、判断阈值和简短原因；
- 模型调用耗时、Token 用量、循环次数和终止原因。

分析区展示实际输入、可记录状态和结构化结果，不依赖或展示模型不可获得的内部
思维链。

## 3. 核心产品模型

### 参与者

- 一名真人用户。
- 两个固定、角色明显不同的轻量 LLM Agent。
- Agent 由简单模型调用和 loop 构成，不使用 coding agent、复杂工具链或自主
  任务系统。

### 中心化话题链

- server/daemon 维护消息、话题内容、话题链及其状态，作为共享事实来源。
- 话题链具有 active/inactive 状态。
- 新消息可以延续当前话题、插入完全无关的新话题，或重新激活旧话题。
- “打岔”是预期行为：真实群聊不要求所有消息始终围绕同一话题。
- 每个 Agent 不复制或拥有独立话题事实，而是用索引组织“自己眼中”的话题链，
  据此选择与角色和当前消息有关的上下文。
- 一条消息如何关联一个或多个话题、多个话题能否同时 active，以及激活/失活
  算法，由架构阶段给出最小方案和权衡。

### Agent 响应决策

每条用户或 Agent 消息进入后，两个 Agent 都独立判断截至当前是否需要回应。
系统至少记录：

- `should_reply`；
- 可比较的参与评分；
- 当时使用的阈值；
- 简短、结构化的原因；
- 选中的话题链和上下文快照。

沉默是一等结果，同样需要记录，但不作为消息显示在聊天区。

### 有界自动接力

- Agent 回复作为新消息再次进入话题归类、上下文选择和响应判断流程。
- 自动接力在无人需要回应时自然停止。
- 同时设置最大 Agent 消息数、最大循环数、Token 上限和超时。
- 达到任一上限或用户停止后，不得继续触发回复。

具体默认数值由架构阶段结合模型调用成本提出，首版演示目标约为 3～5 条 Agent
消息。

## 4. 数据与复盘

首版使用数据库保存只读复盘所需信息：

- 会话与消息；
- 话题链、状态变化及消息关联；
- 每个 Agent 的话题索引；
- 每次实际上下文快照；
- 回应/沉默决策、评分、阈值和原因；
- 模型、耗时、Token 用量、循环及终止原因。

首版支持浏览历史运行并逐步查看决策链，不要求从任一步重新运行、分叉实验或保证
模型输出可复现。

## 5. 首版用户故事

1. 作为实验者，我发送一条消息后，可以看到两个 Agent 像群成员一样自行决定
   回应或沉默，而不是固定轮流发言。
2. 作为实验者，我可以临时插入无关话题，再回到旧话题，观察系统创建、失活和
   重新激活话题链。
3. 作为实验者，我可以选择任一消息和 Agent，检查它当时使用了哪些上下文、
   为什么回应或沉默。
4. 作为实验者，我可以查看历史运行，复盘话题链、响应决策、Token 和终止原因。
5. 作为实验者，我可以随时停止自动接力，并确认系统不会无限消耗 Token。

## 6. P0 范围

- 单页桌面 Web 实验台：聊天区 + 分析区。
- 固定一名用户、两个 Agent 和两个不同角色设定。
- 文本消息与基本生成状态。
- 中心化话题链及 active/inactive 状态。
- Agent 话题链索引与上下文快照。
- 每条新消息后的独立回应/沉默判断。
- 有界自动接力与手动停止。
- 数据库存储和只读历史复盘。
- 模型耗时、Token、循环和终止原因记录。

## 7. 非目标

- 通用 Agent 创建器、Agent 市场或外部 Agent 接入。
- coding agent、工具调用、代码执行或外部系统操作。
- 多用户实时协作、账号体系、权限、计费或多租户。
- 原生移动端、语音、视频、附件或复杂富媒体。
- 长期人格记忆、知识库和跨会话自主任务。
- 历史节点重新运行、实验分叉和严格可复现。
- 生产部署、SLA、运维后台或商业发布时间。

## 8. 验收场景

至少完成一组可重复演示：

1. 用户开启话题 A。
2. 两个 Agent 基于角色和上下文产生回应或沉默，回复顺序不是固定 A/B 轮流。
3. 用户以 “by the way” 等方式打岔并开启无关话题 B。
4. 系统保留 A 的话题链状态，创建或激活 B。
5. 用户重新提及 A，系统重新激活 A，并为两个 Agent 恢复适当的 A 上下文。
6. 对话中出现至少两类自然群聊行为：回应彼此、追问、主动补充、打岔、连续
   发言或选择沉默。
7. 分析区可以逐步查看每次话题路由、Agent 上下文、回应/沉默决策和调用指标。
8. 自动接力在无人回应、用户停止或达到任一硬上限时结束。
9. 刷新后可以读取该次运行用于复盘，但不要求继续原对话或重新运行某一步。

## 9. 架构阶段输入与交付要求

架构师基于本简报完成：

- 前端、server/daemon、数据库和模型调用的最小组件边界与数据流；
- 消息、话题链、激活状态、Agent 索引、上下文快照和响应决策的数据模型；
- 话题创建/关联/激活/失活的首版策略与备选方案；
- Agent 上下文选择和回应决策的最小可验证方案；
- 自动接力状态机、并发策略及硬性成本边界；
- 分析区所需事件与查询接口；
- 数据库、前后端框架、模型接入和本地运行方式的技术选型及权衡；
- 面向后续设计、开发和测试的阶段拆分、依赖和验收建议。

架构阶段不实现业务代码，不启动生产部署，也不把首版扩展成通用 Agent 平台。
